### 1. わかったこと (核心的な理解)

🔸 **Lighthouse＝品質の自動監査レポート**

* **DevToolsとの一体利用:** Lighthouse タブから「ページ読み込みを分析」を実行すると、Performance / Accessibility / Best Practices / SEO の各カテゴリが 0〜100 点で採点される。PageSpeed Insights も同じ Lighthouse エンジンを使っており、ブラウザ内で完結して手軽に診断できると理解した。
* **「点数＝改善の優先順位」:** 赤・黄・緑のスコアだけでなく、不合格項目ごとに「なぜ重要か」「どう直すか」が示される。感覚ではなく数値と根拠で改善箇所を選べる点が実務向きだと体感した。
* **Google のページ体験（Page Experience）:** Webマスター向け公式ブログで、パフォーマンス指標が検索評価の一部として位置づけられている背景を整理。Lighthouse は SEO カテゴリだけでなく、表示速度・操作性まで含めた「ユーザー体験の健康診断」だと捉え直した。

🔸 **Performance の6つの測定基準（Core Web Vitals 周辺）**

* **FCP（First Contentful Paint）:** 最初のテキストや画像が描画されるまでの時間。ユーザーが「読み込みが始まった」と感じる最初の瞬間。
* **LCP（Largest Contentful Paint）:** 最大のコンテンツ（ヒーロー画像など）が表示されるまでの時間。体感速度に最も効く指標の一つ。
* **Speed Index:** ページ全体がどれだけ早く視覚的に完成するかを表す総合的な速度指標。
* **TTI（Time to Interactive）:** 見た目は出揃ったが、まだ JavaScript の処理で操作できない「固まった時間」を可視化する。
* **TBT（Total Blocking Time）:** メインスレッドが長時間ブロックされ、入力への応答が遅れる合計時間。
* **CLS（Cumulative Layout Shift）:** 読み込み中にレイアウトがずれてボタンを押し損ねる、といった「見た目のブレ」を数値化する指標。

🔸 **重み付けとライブデモで見えた改善の型**

* **スコアは指標ごとに重みが異なる:** 6 指標は単純平均ではなく、LCP や TBT など影響の大きい項目ほど Performance 全体の点数に効く。どこを直すと点数が伸びやすいかの判断材料になる。
* **よくある対策パターン:** デモでは画像の圧縮（TinyPNG 等）、不要 CSS の削減（PurgeCSS 等）で LCP や FCP が改善し、スコアが上がる流れを確認。Application で見た Cache / Service Worker の設定とも接続し、「キャッシュ＋アセット最適化＝Performance 向上」の線が一本につながった。
* **前回 Application との接続:** Service Worker や Cache Storage で静的ファイルを効かせると、再訪問時の LCP / Speed Index に効く。Elements で DOM を、Sources で JS を、Application で永続化を、Lighthouse で総合採点——DevTools 各パネルの役割分担が揃った感覚。

### 2. 次やること (自力で発見する課題)

* **自作 or よく使うサイトで Lighthouse を実行:** モバイル / デスクトップ両方のスコアを記録し、赤項目トップ3をメモする。
* **画像・CSS 改善のミニ実験:** 1枚の画像を圧縮して差し替え、LCP がどれだけ変わるか Before/After で計測する。
* **次回（動画5）の予習:** セキュリティ＆ネットワーク機能（Network パネル）に触れ、通信の遅延が Performance 指標にどう効くかを意識する。

### 3. 感想 (内省)

7/15 の「次やること」に書いていた Lighthouse 予習が、そのまま本編で回収できた一日でした。Elements・Sources・Application と続けてきた DevTools シリーズの中で、Lighthouse は「各パネルで触った個別の改善が、最終的にユーザー体験の点数としてどう返ってくるか」を俯瞰するパネルだと理解できました。
